# Packaging

`packages/flutter_mapigrade/darwin/flutter_mapigrade/Package.swift` declares `MaplibreNativeC` as a remote binary target: the `MaplibreNativeC.xcframework.zip` of the MapLibre Native FFI release in `packages/flutter_mapigrade/maplibre_ffi.lock`, with its checksum. Swift Package Manager downloads and caches the zip, and Xcode links the framework into the app, embeds it in `Contents/Frameworks/` and signs it. When the symlink `Frameworks/MaplibreNativeC.xcframework` resolves to a local FFI build in `third_party/`, `Package.swift` uses that framework in place of the zip (`CONTRIBUTING.md`, "Build MapLibre Native FFI"). Until the publish-readiness change the framework was named `MapLibreNativeC`, and the package always used the local build; the checks below from before 2026-10-20 name it so. The plugin's C++ core (`src/core/`, also a symlink) and the Metal bridge are compiled into the app executable, which exports the `map_texture_*` functions that Dart binds with `@Native`.

On iOS, Xcode embeds and signs the framework in `Runner.app/Frameworks/`. The test harness is arm64 only, because the zip's macOS and iOS simulator slices are arm64 only: `ARCHS = arm64` in `packages/test_harness/macos/Runner/Configs/AppInfo.xcconfig`, and `EXCLUDED_ARCHS[sdk=iphonesimulator*] = x86_64` in `packages/test_harness/ios/Flutter/Debug.xcconfig` and `Release.xcconfig`.

Xcode removes every global symbol from the app executable when it archives the app, because `STRIP_STYLE` defaults to `all` and archiving sets `DEPLOYMENT_POSTPROCESSING`. Dart's `@Native` lookup and `nativeLibraryAvailable` then can't find `map_texture_create`, so an app must set `STRIP_STYLE = non-global` for the `Runner` target's Release and Profile configurations (plugin README, Supported platforms). `flutter build` and `flutter run --release` don't set `DEPLOYMENT_POSTPROCESSING`, so their executables keep the symbols. The release build check below used such a build. The examples and the test harness don't set `STRIP_STYLE`.

iOS release build check (2026-10-10): the executable exports all `map_texture_*` functions that Dart binds (`dyld_info -exports`), it loads `@rpath/MapLibreNativeC.framework/MapLibreNativeC` with `@executable_path/Frameworks` as an `LC_RPATH` entry, and the release build displays the map on an iPhone 15 Pro Max.

Release build check (2026-10-09): `otool -L` on the executable shows `@rpath/MapLibreNativeC.framework/Versions/A/MapLibreNativeC`, the only `LC_RPATH` entries are `/usr/lib/swift` and `@executable_path/../Frameworks`, `codesign --verify --deep --strict` passes, and a copy of the `.app` outside the build directory starts and shows the map. In the release bundle, `MapLibreNativeC.framework` takes 12,884 KB of 49,952 KB.

## Android

`packages/flutter_mapigrade/android/` is a Gradle library module (`minSdk` 29, `ndkVersion` 30.0.16248370, `abiFilters` `arm64-v8a`, `armeabi-v7a` and `x86_64`). It depends on the runtime AAR of the MapLibre Native FFI release in `maplibre_ffi.lock`, `org.maplibre.nativeffi:maplibre-native-ffi-runtime-opengl-android`, from Maven Central. Its CMake build (`android/src/main/cpp/CMakeLists.txt`) compiles the C++ core and the Android render target into `libflutter_mapigrade.so`, and links it against `libmaplibre-native-c.so`, which it finds through the AAR's Prefab module `maplibre-native-c` with `find_package`. Gradle packages both libraries in the APK under `lib/<abi>/`: the plugin's from the CMake build, and the FFI's from the AAR's `jni/`. Both libraries link the NDK's C++ runtime statically (`c++_static`); only the C ABI crosses between them. The `arm64-v8a` and `x86_64` libraries have 16 KB segment alignment, which devices and emulators with 16 KB pages require.

The AAR also contains the FFI's patched `rustls-platform-verifier` Android classes and their keep rules. The APK needs them, because `mln_android_init` uses them to verify TLS certificates with the Android platform verifier.

When the Gradle property `mapigrade.ffiDir` names a local FFI build, which the example, the demo app and the test harness set in their `android/gradle.properties`, the module uses that build in place of the AAR: it links the local library as an imported library, packages it through a generated `jniLibs` directory for the ABIs of the installed Android presets, and depends on the verifier in the file-based Maven repository `third_party/maplibre-native-ffi/android-maven/`. Gradle logs which of the two it uses.

The plugin class loads `libflutter_mapigrade.so` with `System.loadLibrary`. The package's build hook (`hook/build.dart`) declares the same library as a code asset with link mode `DynamicLoadingSystem`, so Flutter adds no file to the APK, and Dart's lookup by name returns the library that is already loaded (design D56 of the android-texture-vertical-slice change).

Android release build check (2026-10-20, FFI release 0.202610.1, Prefab): the test harness's release APK (86.1 MB) contains `libflutter_mapigrade.so` and `libmaplibre-native-c.so` for `arm64-v8a`, `armeabi-v7a` and `x86_64`, each `libmaplibre-native-c.so` byte-identical to the AAR's, and each `libflutter_mapigrade.so` needs `libmaplibre-native-c.so`. The integration tests `map_layer_test.dart` and `map_texture_test.dart`, in debug builds, passed on an arm64 emulator.

Android release build check (2026-10-16, local build at FFI commit `677a1cfdf1ab2b914f633d4abc790b7136d3a321`): the release APK contains `libflutter_mapigrade.so` and `libmaplibre-native-c.so` for `arm64-v8a` only, stored uncompressed, and the release build starts on a Pixel 4a (5G) with Android 14, logs a successful `mln_android_init`, and shows the map with a style and tiles loaded over HTTPS. Sizes are in `limitations.md`.
